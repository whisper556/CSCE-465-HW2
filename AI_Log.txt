4. Explaining the key derivation

User: could you explain these and where you used them: K_master = SHA-256("CSCE465-KDF-v1" || Z || TH) / K_g2n_enc = ... / K_g2n_mac = ... / K_n2g_enc = ... / K_n2g_mac = ... / session_id = first 8 bytes of HMAC-SHA-256(K_master, "session identifier" || TH)

Claude: Explained that these are the assignment's key-derivation steps, implemented in derive_keys() in handshake.py.

Inputs: Z is the raw DH shared secret (384 bytes), not safe to use directly as a key; TH is the SHA-256 of the canonical transcript, which ties every key to this exact authenticated exchange; || is byte concatenation.
K_master: compresses Z into a uniform 256-bit secret bound to the session. The label CSCE465-KDF-v1 provides domain separation. Plain concatenation is safe because all fields have fixed widths (label constant, Z 384 bytes, TH 32 bytes). It is never stored.
Five outputs: each is HMAC-SHA-256(K_master, label || TH); the labels make them independent. A table mapped them to the record layer: K_g2n_enc/K_g2n_mac for gateway→node records, K_n2g_enc/K_n2g_mac for node→gateway, and session_id for the first 8 bytes of the IV.
Why separate: encryption and MAC use different keys; each direction has its own keys so that, with sequence numbers starting at 0 in both directions, the two directions do not share a CTR keystream, and reflected records fail; session_id is public, unique per session.
Where used in code: Party._bind() computes TH and Z; Party._derive() calls derive_keys() only after the peer's RSA-PSS signature verifies; both sides get identical SessionKeys.
Said that Task 3 would take these keys. (See entry 7 for a correction about the wording.)

16. IV reuse

User: could explain further how the system avoids reuse of IVS

Claude: The requirement is that a (key, IV) pair never repeats, achieved in layers:

Within a direction of a session: the IV is session_id || sequence from the sender's local counter, which starts at 0, only increases, is advanced only after a record is built, and raises an error when exhausted rather than wrapping (2^32 by default, 2^64−1 with the literal layout). A failed seal() does not advance it.
Across directions: both start at sequence 0 with the same session_id, so IVs coincide, but each direction has its own key, so (key, IV) pairs stay unique.
Across sessions: fresh keys per session (K_master depends on Z and TH), and session_id differs per session.
Within a record: the counter-block overlap issue and the SAFE_CTR_BLOCK fix.
Listed the relevant tests, and honest limits: not thread-safe, rolled-back state could rewind the counter (a restart means a new handshake), and uniqueness depends on correct sender behavior, not receiver enforcement.
17. Counter block detail

User: can you further explain the counter block detail

Claude: Explained that CTR encrypts a 128-bit counter value per 16-byte block and XORs the result with the plaintext, so a record uses a range of counter values. With the literal iv = session_id || sequence as the starting block, record n uses counter values S|n, S|n+1, ... so a 48-byte record at sequence 0 (S|0, S|1, S|2) overlaps a record at sequence 1 (S|1, S|2, S|3); the starting IVs differ but blocks share keystream, so C₀ ⊕ C₁ = P₀ ⊕ P₁ for the overlap. Any record over 16 bytes is affected, and the MAC does not help because the leak is in confidentiality. The fix starts the counter at session_id || (sequence << 32), giving each record its own 2^32-block window (the 1 MiB MAX_PLAINTEXT can never reach the end). The costs are the sequence limit of 2^32. The MAC-covered iv, header, and tag are unchanged. Compared with AES-GCM's 96-bit nonce plus 32-bit counter, and noted test_consecutive_records_do_not_share_keystream and the earlier check with SAFE_CTR_BLOCK = False.

18. Independent keys

User: could you explain this more: 4. Why independent encryption and MAC keys (~90 words) ... (pasted the outline bullets)

Claude: Explained: least privilege (a verifier holding only the MAC key can't decrypt), damage containment, and that the Encrypt-then-MAC security proof assumes independent keys (mixing AES-CTR and HMAC under one key is not covered by the proof; no known break is claimed). Keys are derived with distinct HMAC labels. On directions: both directions start at sequence 0 with the same session_id, so a shared encryption key would reuse IV and keystream. Correction to its earlier outline: Claude had written that shared keys "would let an attacker reflect records"; it said this overstates it, because the direction byte is covered by the MAC, so reflection fails even under a shared key. The more accurate claim is defense in depth: separate directional keys make a reflected record fail the MAC even if the direction check were bypassed. Cited test_gateway_record_reflected_to_gateway_rejected and test_reflected_record_with_relabelled_direction_rejected.
